# История ошибки с default.pem

Для текущего Reference-сервера используйте [новую утилиту 2.0.0 и инструкцию mylocal.pem](reference-certificate.md).
Следующий текст описывает прежнюю неудачную попытку на MIDSERV.

> **Статус на 21 октября 2026 года: прямая замена `default.pem` не решила проблему на сервере пользователя. Не повторяйте `install` и остановку MIDSERV по инструкции ниже.**
>
> Пользователь подтвердил успешное выполнение `install` и импорт нового сертификата. После запуска MIDSERV (новый PID 19000) проверка показала: `NewFileHash` — `False`, `OriginalFileHash` — `True`. Рабочий файл был восстановлен побайтно до прежнего состояния. Новый сертификат в папке подготовки действителен до 21.10.2028; сервер продолжает предъявлять сертификат 2013–2014 годов.
>
> Совпадение исходного отпечатка подтвердило содержимое файла, но не подтвердило, что его можно постоянно заменить таким способом. Кто именно восстанавливает файл при запуске и как выбрать пользовательский PEM в этой сборке, пока не установлено. Нужна документированная настройка HTTPS-модуля R-Keeper либо ответ поддержки UCS. Не угадывайте имена параметров и файлов и не отключайте проверку TLS.
>
> Сохраните папку подготовки с новым сертификатом и резервной копией. PEM-файлы содержат закрытые ключи; не отправляйте их в поддержку. Для обращения достаточно версии MIDSERV/HTTP-модуля, пути `midbase\httpKeys\default.pem`, исходного отпечатка и результата проверки восстановления. Хранилище доверия Windows и повторный выпуск сертификата это восстановление не устраняют.

## Уточнение по официальной документации сервера справочников

После восстановления доступа к docs.rkeeper.ru 21.10.2026 прочитана статья
[«Использование валидных SSL-сертификатов для сервера отчетов в домене»](https://docs.rkeeper.ru/pages/viewpage.action?pageId=77467573).
В ней явно указано: пользовательский PEM с сертификатом и закрытым ключом должен называться
**`mylocal.pem`** и находиться в каталоге `BaseData\httpKeys`, рядом с `default.pem`.
После настройки требуется перезапуск сервера отчётов. Поддерживаются RSA 2048 и SHA256.

Предыдущая попытка заменить `default.pem` не соответствовала этому порядку.
Команда `install` утилиты 1.0.0 по-прежнему пишет именно в `default.pem` и **не реализует**
описанный способ настройки `mylocal.pem`; повторять её для этого не нужно.

Область действия найденной статьи — сервер отчётов/справочников. Её применимость к
кассовому MIDSERV в этой сессии не проверялась. У пользователя теперь требуется именно
Reference-сервер: позднее подтверждены `192.168.7.2:8010`, процесс `RefSrv.exe` и каталог `base\httpKeys`.
Путь `midbase\httpKeys` прежнего кассового сервера нельзя автоматически считать путём реф-сервера.

Перед практической настройкой нужны действующий сертификат с именами/SAN фактического
адреса подключения, соответствующий закрытый ключ и проверенное доверие на компьютере клиента.
Наличие нового файла и импорт `.cer` недостаточны: после согласованного перезапуска нужно
сверить отпечаток сертификата, фактически предъявляемого нужным процессом/портом.
Проверку TLS приложение сохраняет. Реальная настройка Reference-сервера ещё не выполнена.

## Историческая процедура, не подтверждённая после перезапуска

Следующий текст сохранён для воспроизводимости уже выполненных действий. Он **не является рекомендацией повторить установку** на указанном сервере.

[Скачать утилиту 1.0.0, Windows x64, ZIP](https://github.com/lemeschenkoartem/kushat/raw/refs/heads/downloads/Kushat-CertificateTool-1.0.0-win-x64.zip).
Распакуйте архив в отдельную папку. .NET отдельно устанавливать не требуется.

Это вспомогательная утилита проекта «Кушать», а не официальная утилита UCS.
Совместимость нового файла с конкретной сборкой MIDSERV подтверждается только проверкой после перезапуска.
Формат сохранён: RSA PRIVATE KEY (PKCS#1), затем CERTIFICATE, PEM без пароля.

Исходное совпадение подтверждено диагностикой пользователя: HTTPS `127.0.0.1:8086` предъявляет
тот же сертификат, который находится в `midbase\httpKeys\default.pem`:
SHA256 `E386054B1BBC16C3F4D54C95D03CB1CCD97E317B0B1AE7EC622179A75A447A8B`,
CN `rk7.local`, срок 23.09.2013–23.09.2014.
Одного добавления этого сертификата в доверенные недостаточно: срок истёк, IP отсутствует в SAN.
Утилита предназначена именно для этого случая и отклонит другой исходный сертификат.

## 1. Подготовить без остановки сервера

Проверьте дату и время Windows. Откройте PowerShell от имени администратора
под той же учётной записью Windows, которой принадлежит папка подготовки.
Перейдите в распакованную папку, содержащую `Kushat.CertificateTool.exe`.
Выполните:

```powershell
.\Kushat.CertificateTool.exe prepare 'C:\rkeeper\R Keeper 7 Cash\788\Rk7MidServer'
```

Утилита не меняет рабочий файл и не управляет службами. Она создаёт папку
`midbase\httpKeys\Kushat-renewal-<время>-<идентификатор>` с доступом только для текущего
пользователя, администраторов и SYSTEM. Внутри:

- `default.before.pem` — точная резервная копия исходного файла;
- `default.new.pem` — новый уникальный ключ RSA 2048 и сертификат SHA256;
- `rkeeper-local.cer` — только публичный сертификат;
- `certificate-info.txt` — отпечаток и срок нового сертификата;
- `preparation.json` — пути и контрольные суммы для проверки перед заменой.

Срок нового сертификата — два года. SAN: `127.0.0.1`, `::1`, `localhost`, `rk7.local`.
Для подключения с другого компьютера нужен сертификат с фактическим именем/IP сервера;
этот вариант рассчитан на программу и MIDSERV на одном компьютере.
Не отправляйте PEM-файлы в чат, GitHub, почту или систему заявок: они содержат ключи.
Сохраните резервную копию до проверки эксплуатации.

В том же PowerShell сохраните путь **из вывода prepare** в переменную:

```powershell
$rkPrepared = 'ПОЛНЫЙ ПУТЬ К ПАПКЕ ПОДГОТОВКИ ИЗ ВЫВОДА'
```

## 2. Заменить в согласованное время

Остановка MIDSERV прерывает обслуживание касс. Выполняйте замену, когда кассы не используются,
штатным способом остановки вашего сервера. Не завершайте процесс принудительно.
Если сервер работает как служба, остановите соответствующую службу через `services.msc`.
Не запускайте его повторно до завершения команды установки.

```powershell
.\Kushat.CertificateTool.exe install $rkPrepared
```

Команда откажет, если на компьютере запущен хотя бы один процесс MIDSERV,
если рабочий файл изменился после подготовки или файлы подготовки не прошли проверку.
Она проверяет соответствие нового ключа сертификату, срок, самоподписанную цепочку и серверный EKU.
При записи в существующий файл сохраняются его владелец и права доступа.
При обычной ошибке записи выполняется попытка немедленного восстановления прежнего содержимого.
Защита от внезапного отключения питания не гарантируется: резервная копия остаётся в папке подготовки.

После сообщения об успешной замене запустите MIDSERV привычным способом.
Замена меняет сертификат HTTPS для всех клиентов этого экземпляра сервера;
клиентам, использующим системную проверку TLS, также потребуется доверие к новому сертификату.

## 3. Добавить доверие к новому сертификату

Под пользователем Windows, который запускает приложение «Кушать», откройте
`rkeeper-local.cer` из папки подготовки. Сверьте SHA256 во вкладке «Состав»
с `certificate-info.txt` (если окно показывает только SHA1, используйте команду ниже).
Нажмите «Установить сертификат» → «Текущий пользователь» → «Поместить все сертификаты
в следующее хранилище» → «Доверенные корневые центры сертификации» → «Готово».
Утилита сама хранилище Windows не изменяет.

```powershell
certutil -hashfile "$rkPrepared\rkeeper-local.cer" SHA256
```

Если подготовка выполнялась под другой административной учётной записью,
передайте пользователю приложения только публичный `.cer`; закрытые ключи и резервную копию не передавайте.

## 4. Проверить до ввода пароля

Из-под пользователя приложения выполните без `-k`:

```powershell
curl.exe -v --max-time 10 https://127.0.0.1:8086/rk7api/v0/xmlinterface.xml
```

HTTP 401 без ошибок сертификата означает, что TLS прошёл и сервер требует авторизацию.
Другой HTTP-ответ также нужно оценивать отдельно: GET не проверяет выполнение XML-запросов.
Если предъявляется прежний отпечаток — не меняйте порт или проверку TLS:
проверьте, тот ли экземпляр MIDSERV был остановлен и запущен.

В приложении «Кушать» оставьте `https://127.0.0.1:8086` и выполните вход.
HTTP 401/403 после исправления TLS относится к учётной записи и правам, а не сертификату.
Успешная загрузка номенклатуры пока не проверена на сервере пользователя.

## Откат

Если MIDSERV не запускается или новый PEM не принимается, штатно остановите сервер и выполните:

```powershell
.\Kushat.CertificateTool.exe rollback $rkPrepared
```

Утилита восстановит исходный файл после проверки резервной копии и текущего содержимого.
Затем запустите сервер штатным способом. Старый сертификат снова будет просроченным,
но прежнее состояние сервера восстановится. Если файл повреждён аварийным отключением
и проверка отката отказывает, при остановленном сервере восстановите содержимое
`default.before.pem` в исходном `midbase\httpKeys\default.pem` с сохранением его прав доступа.

## Воспроизводимая сборка

```powershell
dotnet publish tools/Kushat.CertificateTool/Kushat.CertificateTool.csproj -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true -p:DebugType=None -p:DebugSymbols=false -o artifacts/certificate-win-x64
```

Проверки генератора входят в `scripts/check.sh`: корректность ключа/сертификата,
срок и реальные TLS-сеансы с проверкой SAN для четырёх имён/IP.
Подготовка, ACL, замена и откат на Windows и загрузка PEM в реальном MIDSERV требуют
отдельной проверки на Windows; в облачной Linux-среде они не проверены.
